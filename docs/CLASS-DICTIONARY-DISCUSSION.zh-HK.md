# 領路通類別整理及字典討論稿

日期：2026 年 10 月 22 日。狀態：Dataset 工作建議，供組員覆核；不是已定案字典，不代表已訓練或通過視障使用者驗證。

建議主物件模型 A 採 6 個現有 COCO 類別及 17 個自訂類別，共 23 類候選；牌內圖示模型 B 另有 12 類候選。OCR 使用另一條按需文字流程。先完成定義與資料覆核，再按成熟度分批訓練，不為湊數一次開齊所有類別。

本稿根據目前 App、較早的類別審核及本地後端字典核對。組員已說明最新 OneDrive 字典刻意未放 Official define；該最新檔尚未核對。本地副本的舊 Official 數量與分類問題不能當成最新檔仍有同樣問題。原始 FYP／工作表是構想來源，不是已訓練清單。

## 1 先分清字典 類別來源及模型輸出

COCO 80 類可繼續保留在字典作登記，但模型只輸出訓練 profile 啟用的子集。person／行人／pedestrian 是同一 canonical 類別；不在 Official define 再建一份。COCO 類別仍可加入香港照片微調，沿用類別不等於不用補本地資料或模型會自動保留舊能力。

之前 20 類方案把四種道路車輛併為 road_vehicle。本稿建議沿用四個 COCO 類別，再在 App 播報層按需要統稱車輛；road_vehicle 只作結果群組，不作額外訓練類別。因此 20 − 1 ＋ 4 ＝ 23。這是為配合不重複登記 COCO 的設計選擇，並非認定拆分必然較準確。

模型 A 及 B 各自用 YOLO11n 偵測版作第一輪基線；它們是兩份獨立權重，不按街道／商場拆兩個環境模型。現有九類 TFLite 不改；A 的新候選 profile 與 B 均未訓練。

## 3 Official define 建議清單

以下 17 類未由 COCO 80 類提供相同定義，建議作正式自訂類別候選。鍵名尚可在開會時統一，正式 ID 留空；舊 App ID 只在 JSON 作遷移對照。

| 建議 key 與中文 | 納入範圍 | 排除及合併界線 |
|---|---|---|
| bin 垃圾桶 | 不同大小、形狀、顏色及場景的垃圾桶 | 不含水桶、花盆或一般箱子；保留 rubbishBin／rubbish bin 作來源別名 |
| bollard 護柱 | 用來限制通行的矮柱或護柱本體 | 與一般固定細柱擇一標註；不按顏色另開 class |
| traffic_cone 交通錐 | 獨立錐形交通錐 | 不再標臨時路障父類；連接桿另記難例 |
| caution_slippery 小心地滑告示 | 可確認為地滑警示的獨立告示本體 | 不等於地面濕滑；wet_floor_sign 為來源別名，不再標一般指示牌 |
| stairs 樓梯 | 整段連續梯級 | 合併 upstairs／downstairs；不逐級重標 step，方向只作覆核屬性 |
| escalator 扶手電梯 | 同一設備的可見扶手、梯級及結構 | 室內外合併；不由靜態 class 判斷運行或准入方向 |
| temporary_barrier 臨時路障 | 用途可確認的臨時阻隔設施，包括水馬與臨時硬式圍網 | 不含交通錐、護柱、固定圍欄；看不出是否臨時者先待覆核 |
| fence 固定圍欄 | 固定圍欄與欄杆 | 天橋欄杆可合併；不靠材質判斷固定性，不與臨時路障重標 |
| push_cart 載貨手推車 | 一般平台或籠式載貨手推車 | 嬰兒車、購物車、兩輪搬運車、唧車不無條件併入 |
| step 單級台階 | 孤立、單級的高度變化 | 整段樓梯只標 stairs；路緣及斜道邊界另記困難案例 |
| elevator 升降機入口 | 有門框、門及周邊設施證據的實體升降機入口 | 不是圖示；同一入口不再重標一般門，難以確認用途則待覆核 |
| ramp 斜道 | 可見且可辨識的坡面區域 | 不因拍攝透視傾斜就標斜道；不保證無障礙可通行 |
| tactile_paving 盲道 | 可見引導或警示觸覺鋪面 | 引導／警示、材質、顏色作屬性；不當成已驗證路線 |
| zebra_crossing 斑馬線 | 可見過路斑馬線區域 | 不是 COCO 動物 zebra；不判斷燈號或可否過路 |
| door 一般門 | 一般門或可辨識門洞 | 玻璃門合併並獨立測試透明外觀；不含可確認的升降機入口 |
| sign_pictogram 設施方向指示牌 | 包含設施圖示或導向文字的整塊實體牌面 | 不是所有廣告；不是 COCO stop sign；牌內圖示交 B，文字交 OCR |
| fixed_pole 固定細柱 | 路燈柱、標誌桿等人工固定柱身 | 原框含燈頭或牌面時須重畫，不直接換標；不含護柱及一般樹木 |

暫不新增 pedestrian、vehicle、road_vehicle 等與既有選定類別重疊的 Official 輸出。water_filled_barrier／barrier_fencing、upstairs／downstairs、室內外 escalator、玻璃門等保留來源名稱及屬性，只有經覆核符合共同定義才合併。

嬰兒車、兩輪搬運車、唧車、一般樹木／倒木、坑洞、懸空障礙、鷹架、街邊雜物、桌椅泛類等不硬塞進現有候選；另留需求／困難案例。桌與椅若日後納入，先沿用 COCO 的 chair／dining table 等實際定義，不再設模糊的 tables_and_chairs。

## 4 sign icon v1 建議清單

B 對同一牌面找多個圖示及箭嘴，每個圖示各一框；不是整塊牌只輸出一個分類。獨立 sign-icon-v1 命名空間，不把圖示當 A 的實體人、門或扶手電梯。

| 建議類別 | 中文 | 標註與解讀界線 |
|---|---|---|
| male_symbol | 男士圖示 | 設施牌內的男性符號；不是辨識真人性別 |
| female_symbol | 女士圖示 | 設施牌內的女性符號；不是辨識真人性別 |
| wheelchair_symbol | 輪椅／無障礙圖示 | 只辨識標記，不保證設施可用 |
| toilet_symbol | 一般洗手間圖示 | 不表示男或女；只有 WC／文字者交 OCR |
| lift_symbol | 升降機圖示 | 牌內設備圖示，不是實體入口 |
| escalator_symbol | 扶手電梯圖示 | 不推論實際運行方向 |
| stairs_symbol | 樓梯圖示 | 不直接分上樓／落樓 |
| exit_symbol | 出口圖示 | 出口人形等圖案；純文字 EXIT 交 OCR |
| arrow_left | 向左箭嘴 | 依轉正牌面的二維朝向 |
| arrow_right | 向右箭嘴 | 依轉正牌面的二維朝向 |
| arrow_up | 向上箭嘴 | 不直接等於上樓或直行，須結合牌面語境 |
| arrow_down | 向下箭嘴 | 不直接等於落樓或向後，須結合牌面語境 |

男女並列時標兩個圖示，不能再加一個重疊的男女合併類；generic toilet_symbol 只用於一般洗手間符號。輪椅符號可與男女符號各自存在；若是不可分割的複合符號，須先建立共同拆框規則，不能由標註員各自猜。

圖示與箭嘴用 parentSignId、牌面分區／行列及關係標註連結；YOLO TXT 本身不保存這些關係，另存版本化 JSON。只有配對有足夠證據才讀出「男士向左／女士向右」，否則只讀確認到的圖示及「未能確認方向」。

向上箭嘴不能純視覺同時分 forward 與 upstairs；直行、上樓要結合文字與語境。斜箭嘴、U 形箭嘴、港鐵／巴士圖示、扶手電梯入口紅叉／綠箭嘴留作後續候選及範圍外測試，不硬套現有十二類。出口圖案內不可分割的箭嘴是否另框，要按手冊一致處理。

純文字男／女／WC／EXIT、地名、樓層與店名交 OCR，不為每個字詞建立圖示 class。B 的箭嘴增強不可無聲左右翻轉或旋轉；首輪關閉相關增強，若日後使用，必須同步轉換類別及關係標註。

## 5 同一 class 有不同圖片會否有問題

正常的外觀、角度、光線及場景差異是需要的訓練覆蓋，不因長得不同就自動拆 class。真正要先檢查的是定義、框法、資料比例與是否可由影像判斷；以下是本專案的決策方法，不是已量測的訓練結果。

| 情況 | 判斷及處理 |
|---|---|
| 香港橙色街道垃圾桶與商場金屬垃圾桶 | 可同為 bin；記 subtype、scene，分開報告各外觀的漏檢，避免只看總平均 |
| 室內與戶外扶手電梯 | 同為 escalator；天氣、光線、場所作分層，不靠場景再開重複類 |
| 水馬與網式臨時路障 | 共同語意可保留，但外觀差異大；各自抽樣及標註檢查。若其中一種持續差，再比較內部分型或拆類後播報合併 |
| 一般門與升降機入口 | 用途不同；規定同一入口擇一，影像證據不足則待覆核，不交給模型解決標註矛盾 |
| 一張框整座路燈，另一張只框柱身 | 不是有效外觀多樣性；先重畫到 fixed_pole 的同一物件範圍，不能只換 class 名 |
| 很多連拍或不同來源比例懸殊 | 先按實物、地點、工作階段／影片分組去重與切分；控制每種外觀、來源及場景的代表性，不用重複同一影片冒充多樣性 |
| 新圖有未標出的啟用目標 | 補齊全圖所有啟用類，未完成者先隔離。只把舊八／九類 TXT 與新資料拼埋會令漏標目標被當成背景 |
| 真正不屬任何啟用類 | 可作經覆核的背景／範圍外測試；不加一個包羅所有未知物件的 unknown／obstacle 類 |

建議每個爭議合併先抽 30–50 張來自不同實物及場景的代表圖片，兩位組員獨立標註，再覆核分歧；此數量是討論起點，並非樣本充足保證。先比較框法及語意是否一致，再決定是否進入訓練。

訓練時保留 subtype、source、scene、captureSessionId 及覆核狀態。先建立同資料切分的合併版基線；若某個外觀持續漏檢，先查漏標、比例、解析度與域差異，才比較拆分版。比較逐類 precision／recall、混淆、各外觀漏檢及相同 iPhone 條件的效能，不只看整體 mAP。拆分不預設更好，合併也不預設一定學得到。

## 6 訓練批次與字典完成方法

第一批可由現有資料遷移成八類：person、bicycle、bin、bollard、traffic_cone、caution_slippery、stairs、escalator。上／落樓梯合併仍需重查框與屬性，不把舊名稱當成已驗證方向。其餘十五類按資料盤點及需求逐批加入，未納入的類別不建空輸出。B 獨立收集與訓練；先驗證最簡單圖示，再擴充到多圖示及方向關係。

主模型若最終啟用全部候選，A 的本地索引是 0–22；B 為 0–11，各自對應來源命名空間及類別鍵。這些索引只適用本討論 profile，正式 dictionary ID 尚未分配。COCO 的既有字典 ID、App 歷史 ID 及模型本地索引都不能混用。

字典完成次序：取得最新 OneDrive 檔 → 對齊既有 schema 與 COCO 80 項 → 確認 17 個自訂及 12 個圖示定義／取捨 → 分配穩定 registry key／ID → 由實際內容計算 totalClasses → 建立各模型連續索引映射與 aliases → 同步前後端及訓練匯出 → 驗證 JSON 與版本遷移，再交組員覆核。

class_dictionary.proposal.json 是候選資料及 mapping 草稿，不可直接覆蓋正式檔；包含全部 80 項 COCO 取捨、17 個 Official 候選、12 個圖示及兩個模型 profile。正式 ID 為 null，亦不預設一定由 80 或 101 起跳。後端需先確認是否沿用單一全域整數或分命名空間，並遷移目前九類確實已使用的 App 映射。

建議會議確認四項：六個 COCO 與十七個自訂是否符合首輪需求；臨時路障／圍欄／護柱／細柱及門／升降機邊界；十二個圖示與複合符號拆框；第一批資料及訓練分工。未完成這些決定前不稱 final Official define，也不改現有 App 的模型或正式字典。
